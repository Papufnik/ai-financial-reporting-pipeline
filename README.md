# AI-Orchestrated Financial & Ops Reporting Pipeline (Sanitized Demo)

A working, runnable demo of a 4-layer reporting architecture I directed the build of for a real small retail business I run the finance/ops function for. It turns raw operational data into a single plain-language weekly memo an owner will actually read, without ever asking an LLM to compute or invent a number.

This repo runs entirely on synthetic data generated at runtime. No real business's financials, credentials, or vendor data are anywhere in this repo.

```
python run_demo.py
```

That one command generates synthetic data, runs both analysts, runs both Senior Manager synthesis scripts, and writes a finished weekly memo to `data/ceo_weekly_memo.md`. A sample run's output is already committed in `sample_output/` if you'd rather just read it.

## The problem this solves

A small business generates a dozen disconnected reports — inventory turns, cash forecasts, stockouts, discounting, staffing. Someone still has to read all of them, decide what actually matters this week, and explain it in plain language. That's real judgment, and it doesn't scale past one overworked person doing it by hand every week. The question this pipeline answers: how much of that judgment can an AI-directed system do reliably, and where does it need a hard guardrail instead of a "hopefully it's fine"?

## Architecture: 4 layers, each with a narrower job than the one below it

```
Layer 1  Data ingestion            (business-specific, not included here)
Layer 2  Analysts                  layer2_analysts/
Layer 3  Senior Managers           layer3_senior_managers/
Layer 4  CEO Capstone              layer4_capstone/
```

**Layer 2 — Analysts.** Each analyst owns exactly one domain (inventory health, cash forecasting) and outputs plain structured JSON: numbers and labels, no severity, no opinions, no "worth considering" language. `pattern_scan.py` is a shared, domain-agnostic utility any Senior Manager can call to run a systematic Pearson-correlation scan across a category's time series — checking every pair/lag combination the way a chess engine checks moves a human wouldn't bother with, instead of asking an LLM to write speculative prose about "interesting patterns." A hard minimum-sample-size guardrail means a business without enough history correctly gets zero results, not manufactured ones.

**Layer 3 — Senior Managers.** `cfo_synthesis.py` and `coo_synthesis.py` each read their domain's analyst output, apply real numeric thresholds, and decide what crosses into `needsAttention` versus what's fine and shouldn't be surfaced at all. This is where "the AI's opinion" would normally creep in — instead, every threshold is a named constant at the top of the file, and every item is phrased as something worth considering, never a directive. Statistical correlations from `pattern_scan.py` are always tagged `INFO` severity and explicitly excluded from `needsAttention` — a correlation is a lead, not a verified fact, and must never carry the same visual urgency as a real threshold breach.

**Layer 4 — CEO Capstone.** `ceo_weekly_memo.py` reads *only* the two Senior Managers' already-filtered `needsAttention` lists — it does not re-open the raw analyst data or re-derive priority. It combines them, ranks by severity, and writes a short plain-language memo. Every sentence in the structured "Worth a Look" section is a Python f-string built from a real field in the JSON above it. Nothing there is generated by a model.

## The one deliberate exception: a guarded narrative layer

The templated memo above is honest but a little dry. `ceo_weekly_memo.py` has one optional, tightly bounded exception: if an `ANTHROPIC_API_KEY` is set, it will ask Claude Haiku to write a short connective narrative — *using only the facts already assembled in the steps above, handed to it as its sole source material*. The model never computes a number, never looks anything up, and never re-derives a total.

That's the intent. The actual safety comes from `validate_narrative_numbers.py`, which is not a policy, it's a script that checks: it extracts every number the model wrote and cross-references each one against the real numbers already sitting in the verified JSON, with a small rounding tolerance. If even one number doesn't match, the entire narrative is discarded — no partial trust — and the memo silently falls back to the plain templated version. In production, this exact check caught a real rounding slip in the very first sample it was tested against (`$59,417` written where the source fact was `$59,417.61`) before it was ever wired to a live API call.

If there's no API key, no `anthropic` package, an API error, or a failed validation — any of those — the fallback is silent and safe. The JSON output honestly records which happened (`narrativeGenerated: false`, `narrativeFallbackReason: "..."`) rather than pretending the narrative step succeeded when it didn't.

## What I actually did here

I don't write production code from syntax. What I did: specified the exact behavior of every threshold, every severity rule, and the "surface facts, humans decide" constraint that shaped this whole design — no fictional roles get assigned action items at a business with one owner reading this — then directed the AI-assisted implementation and verified it against real data before trusting it.

That verification step mattered in practice, not just in principle. An earlier version of the real CFO synthesis script (`cfo_synthesis.py` here is the corrected version) had seven silent schema-mismatch bugs — reading `overall_gmroi` when the real analyst output the key as `overall`, reading a nested cash object that didn't exist at all, one weekly loan payment even hardcoded as a literal string instead of read from the source file. Every one of those bugs defaulted quietly to `0.0` on failure instead of erroring, so the script ran clean on every scheduled refresh and wrote a JSON file with every number silently wrong, for weeks, because nothing downstream ever checked the values against the source. I found this by manually diffing every field the script read against the analyst's actual output schema — not by trusting that "it ran without an error" meant "it worked." Every field read in this repo's version was checked the same way before being trusted.

## Repo layout

```
generate_synthetic_data.py         synthetic 18-month ledger + ops data (no real business data)
run_demo.py                        orchestrates the full pipeline end to end
layer2_analysts/
  pattern_scan.py                  shared correlation-scan utility
  ledger_monthly_series.py         loads the synthetic ledger's monthly time series
  inventory_health_analyst.py      GMROI + dead-stock detection by category
  cash_forecast_analyst.py         6-month cash forecast, AP, financing, growth trend
layer3_senior_managers/
  cfo_synthesis.py                 finance thresholds -> needsAttention
  coo_synthesis.py                 operations thresholds -> needsAttention
layer4_capstone/
  validate_narrative_numbers.py    the hallucination guardrail
  ceo_weekly_memo.py               reads Layer 3 only, writes the final memo
sample_output/                     a real run's output, committed for quick reading
```

## Stack

Python, `openpyxl` (synthetic ledger + real production version reads real Excel ledgers), `numpy` (correlation math), optionally `anthropic` (Haiku narrative layer — the pipeline runs completely fine without it).

*This is a sanitized, standalone demo of an architecture built and running in production for a real retail business. Business name, real financial figures, and several business-specific analysts (basket/merchandising attachment, payment-integrity reconciliation) have been generalized or omitted to keep this runnable without any real business's data behind it. The threshold logic, severity model, and guardrail pattern are unchanged from what runs in production.*
